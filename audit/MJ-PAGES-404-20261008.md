# GitHub Pages — vérification des 404, 8 octobre 2026

## Observations vérifiées

Les sept URL publiques /Encounter/, /Kentaro/, /Zephyr/, /Samoth/, /Brackmard/, /Rufus/ et /Nans/ ont été ouvertes dans un navigateur cloud neuf. Elles affichent toutes la page GitHub « Site not found » et « There isn’t a GitHub Pages site here », avant tout chargement de l’application. Les fichiers index.html et les derniers commits sont présents dans les dépôts publics. Le champ has_pages vaut true pour les sept dépôts.

## Éléments de déploiement

La liste générale actions/runs accessible via le connecteur renvoie des historiques anciens ou vides. Elle est insuffisante pour conclure à l’absence de déploiement : les checks attachés aux SHAs récents et leurs logs apportent des preuves plus précises.

- Samoth, Zephyr, Brackmard, Rufus, Nans : les checks Pages attachés à leurs derniers SHAs indiquent success. L’existence de ces checks contredit une simple hypothèse de fichiers manquants ou de tous les déploiements échoués.

## Conclusion et blocage

Le symptôme est établi : les URL GitHub Pages ne servent pas les sites, alors que plusieurs déploiements sont déclarés réussis. Pour Kentaro, un build non achevé explique en plus l’absence de déploiement de la dernière version ; il n’explique pas à lui seul les 404 des six autres sites.

La cause racine commune n’est pas établie avec les permissions disponibles. L’API Pages est exclue des endpoints autorisés du connecteur ; la page Settings > Pages n’est pas accessible sans connexion propriétaire. Il faut vérifier l’état actuel de publication, la source et les éventuels messages du compte dans les réglages Pages authentifiés. Aucune désactivation/réactivation, aucun changement de workflow ni suppression de site n’a été effectué sans cette preuve.

Cette vérification ne permet pas de déclarer les sites rétablis. Un succès de commit ou de merge ne prouve pas leur disponibilité publique.
